# SpiderMan2k1Fix — unified development build (NOT A RELEASE)

The single-DLL architecture was merged into `main` through PR #162 on
17 November 2026. This test-only Spider-Man 2001 compatibility launcher
uses one project DLL (`game/fix.dll`), without a local `winmm.dll`.
Native Windows 11 gameplay, DPI-aware 1920×1200 rendering, pointer behavior,
focus-pause and clean shutdown have been observed on real hardware; synthetic
Windows PE32 installation and rollback checks have passed. Equivalent
end-to-end Wine/Proton validation is still outstanding. The published v2.0.0
release is separate and continues to use its earlier WinMM architecture.

**Never use this candidate to modify your existing working installation.**
Use a new empty folder with the test launcher and one legitimate retail ISO/CUE
(with its referenced BIN/IMG when required). No game data is bundled.

## Layout

```text
spiderman2k1fix/
  SpiderMan2k1Fix.exe         # required launcher, installer and verifier
  SpiderMan2k1Fix.ini         # generated by game on first successful launch
  SpiderMan2k1Fix.log
  SpiderMan2k1Fix_installer.log
  SpiderMan2k1Fix_inspect.log # only after --inspect
  state/
    installed-game.sha256
    installed-resources.sha256
  docs/
    README.md
    CHANGELOG.md
    LICENSE
    SDL3-LICENSE.txt      # third-party DLL license
  linux/
    spiderman-focus-helper
  game/
    SpideyPC.exe
    fix.dll
    SDL3.dll              # bundled x86 runtime alongside game executable
    ... original disc files and game-generated files
```

The game runtime `SDL3.dll` lives next to `game/SpideyPC.exe` and `game/fix.dll`. DLL license documentation resides in `docs/`; no `third_party/` directory is installed. Existing unified installations with the former `third_party/SDL3/` layout are **not** migrated automatically: use a separate clean test folder with a legitimate disc image. The old installation is left untouched.

No `mods/` directory is created until actual modding support is implemented.
`state/` contains only two installer-owned SHA-256 receipts; do not edit them.
Screenshots are written beside the launcher when writable. The native X11
focus helper is stored under the launcher's `linux/` directory.

## Downloadable development executable

GitHub Actions now builds the unified launcher as **`SpiderMan2k1Fix.exe`**.
The workflow publishes exactly **one GitHub Actions artifact** named
**`SpiderMan2k1Fix`**, containing only `SpiderMan2k1Fix.exe`.
Synthetic PE32 fixtures and diagnostic executables are exchanged between
Linux and Windows CI jobs through a per-run cross-OS cache, not published as
downloadable artifacts. These internal executables remain necessary to
exercise native Windows installation and rollback safety checks.
The older v2.0.0 installer workflow runs manually only, not on each push.
These development builds are not published releases and should be tested in
an empty folder to preserve an existing installation.

## Commands (experimental)

Use the launcher from the **root**, never `game/SpideyPC.exe` directly:

```text
SpiderMan2k1Fix.exe --version
SpiderMan2k1Fix.exe --inspect original.iso
SpiderMan2k1Fix.exe --install-only
SpiderMan2k1Fix.exe --verify
SpiderMan2k1Fix.exe
```

On Wine/Proton, use the corresponding compatibility launcher to run this
Windows x86 executable; do not copy project DLLs into system folders.

Installation checks the supported original executable's exact SHA-256
(`0a11a49f3f63d4bb15650f322d654553fc47234b01885b852a058ff074689dea`),
then installs the complete original Wise data superset and verified bundled
resources. It stages the five target directories and publishes `state/`
last; on a staging/publish failure it attempts rollback rather than adopting
unrecognized data. A previous `spiderman2001/` installation is **not**
migrated automatically; use a separate test folder.

`--verify` reads both receipts and checks every managed file without
repairing or launching. `--install-only` can upgrade only authenticated
project resources and does not touch original game data, saves or INI.
`--launch-no-verify` skips normal resource-receipt preflight but the unified
startup still **requires the supported original game EXE hash** and the
correct bundled `fix.dll`; it does not bypass the authenticity guard.

`fix.dll` is loaded through a memory-only PE import-name alias in a
suspended process. The on-disk `SpideyPC.exe` is never patched. Native
Windows/Wine WinMM remains the operating-system version.

## Optional F10 cinematic skip

The generated `SpiderMan2k1Fix.ini` has `[Features] F10SkipCinematics=0`.
Set it to `1` while the game is closed to enable **F10** for skipping
opening cinematics, the New Game comic/movie and the two original introductory
3D scripts, using only the game's existing native skip/cleanup paths when
permission is available. Later in-level cinematics are **not yet validated** (unknown native script
owners are not force-skipped), and **F10 does not return from active gameplay
to the menu** in this mode.
The option is independent of `[Debug] Log=1` and applies on the next launch.

Older `[Debug] F10Shortcut=1` is still accepted for existing diagnostic INIs,
but also has the broader legacy gameplay-to-menu action. Keep it disabled if
you want cinematic skipping only. This feature still requires a real Windows 11
regression test before release.

## One-time first-launch diagnostic logging

The installer always writes `SpiderMan2k1Fix_installer.log` beside the
launcher during installation. The **first actual game launch**, when
`SpiderMan2k1Fix.ini` is still absent, automatically writes
`SpiderMan2k1Fix.log` as if **[Debug] Log=1**. The launcher records its
startup first, even before the suspended game process starts; the core
continues the same log after its verified DirectDraw bootstrap.

The generated INI contains **[Debug] Log=0** permanently, so subsequent
sessions do not produce additional runtime logs. The initial log remains
available for diagnosis and is not removed after the game closes. No extra
file is created in `state/`; its only contents remain the two SHA receipts.

An **existing user INI is never changed or overridden**: `Log=1` keeps
logging on every game session; `Log=0` keeps logging off. The first-launch
automatic override applies only if the INI is entirely absent, so placing
a user-configured INI before the first launch honors its setting. If the
first game session crashes after generating an INI, the startup log is
still available and the next launch uses the generated `Log=0`.

**The runtime log contains one game process only, never cumulative
history.** For every new game process with `[Debug] Log=1`, the FIRST core
logging call truncates `SpiderMan2k1Fix.log` and later messages append only
to that current run. The first-launch exception preserves the launcher's
early diagnostic line: the launcher creates/truncates the file before
`CreateProcessW`, and the core appends without truncating that preamble.
`INIT_ONCE` ensures only one reset even if multiple game threads write.
When `Log=0`, the old log is left untouched rather than silently deleted,
but no further game messages are added. To preserve a previous session for
comparison, copy the log elsewhere before launching the next logged run.

The *installer log* and *inspection log* are independent of the in-game
debug switch and each is also reset at its own invocation. They continue
to record verification, installation, updates and launch errors.

## Validation and release boundary

- **Windows 11:** real-game startup, centered DPI-aware 1920×1200 output,
  multi-monitor pointer and focus-pause behavior, sound and clean exit were
  exercised with the unified prototype. This is not a complete regression
  pass across all levels and controller configurations.
- **DirectDraw7 issue #160:** intermittent `SetCooperativeLevel E_FAIL`
  was not reproduced on the latest Windows run. The exact-signature-gated
  DirectSound NULL-cleanup guard investigated in closed PR #161 is included
  in the unified suspended-process bootstrap, but the upstream cause is
  not proven fixed. Keep issue #160 open for recurrence evidence.
- **Wine/Proton:** end-to-end installation, startup, gameplay, SDL3 pads,
  cutscenes, 4:3/widescreen, F9, Alt+Tab/focus, saves and exit still need
  confirmation on the unified architecture.
- **CI:** the unified PE32 and synthetic Windows installation/rollback
  workflow runs on `main` and pull requests, in addition to legacy
  compatibility workflows. CI does not substitute for real-game testing.

Merging PR #162 into `main` did not publish a release; developer artifacts
remain explicitly TEST-ONLY and must not be presented as the v2.0.0 download.

## Retail PE32 import compatibility (17 November 2026)

The SHA-256-supported 1,507,328-byte original `SpideyPC.exe` maps an
approximately 44 MB image (`SizeOfImage=0x02A0D000`). This large virtual
image is normal for its zero-filled data section: it is NOT the size of the
physical EXE file. The suspended-process verifier must match that exact
value, not impose a 32 MB cap.

The genuine `DDRAW.dll` import descriptor has **two functions**:
`DirectDrawCreateEx` at IAT RVA `0x0013B010` and
`DirectDrawEnumerateExA` at `0x0013B014`. The unified
`game/fix.dll` now exports both. It forwards enumeration unchanged to the
Windows/Wine system DirectDraw provider; the game fix starts at the actual
DirectDrawCreateEx factory call. Unknown third imports are rejected.

The launcher reports the result of each check separately (PE import alias,
No-CD, DirectSound NULL Stop guard) and never resumes an unsupported process.
This fixes compatibility with the original PE metadata, but is not proof of
successful gameplay; native Windows and Wine tests remain required.

## DPI-aware geometry (Windows high-DPI / multiple monitors)

The original 2001 EXE has **no embedded RT_MANIFEST**, and is DPI-unaware.
The previous early `winmm.dll` proxy called `SetProcessDPIAware`
*before* the original game window existed. The new single-DLL import-alias
startup intentionally omits that proxy, so Windows 125% scaling otherwise
mixes 1920×1200 DirectDraw physical pixels with a 1536×960 virtualized
monitor rectangle. The resulting menu is offset and clipped.

The unified installer bundles a project-owned *external application manifest*
at `game/SpideyPC.exe.manifest`, declaring **System DPI awareness**. The
original `SpideyPC.exe` byte sequence and SHA-256 remain untouched, with no
global registry changes and no User32 calls from `fix.dll`'s DllMain. This
matches the former proxy awareness level. The manifest is verified as the
eighth project-owned resource in the SHA receipt; it is not a ninth original
game file. The 7-to-8 resource receipt transition is allowed only through
`--install-only` after validating all seven existing hashes and confirming
that no unknown manifest occupies the destination.

A native Windows CI test confirmed external-manifest activation using a
retail-style synthetic EXE: `GetProcessDpiAwareness=PROCESS_SYSTEM_DPI_AWARE`.
Real-game Windows 125% and Wine results still require acceptance testing.

## Unified fix.dll replacement on ordinary launch (no backup)

When an existing installation has authenticated original game files and both
installation receipts, the unified launcher compares `game/fix.dll` to its
embedded project DLL. If they differ (or the DLL is missing), **normal launch
automatically updates the bundled project runtime** and its resource receipt,
then continues into the game. `--verify` remains read-only. Other resource
mismatches alone still require an explicit `--install-only`.

For a changed `game/fix.dll`, the previous bytes are held **only inside the
private transaction directory** to recover from a failed upgrade; after a
successful commit, they are discarded. No new `game/fix.dll.bak` is created
or rotated. Pre-existing `.bak` files are left untouched, because their
contents cannot be authenticated as project-owned. The legacy WinMM/SDL3
backup behavior does not change.

Never overwrite original game files, an unverified installation, or unknown
non-DLL assets. Test fixture includes a forced mid-transaction failure to
check rollback restores the old fix bytes and keeps the receipts unchanged.

## Windows 125% DPI: child-only compatibility fix

A real native Windows 11 1920×1200 test showed that the external
`game/SpideyPC.exe.manifest` was verified and installed, **but ignored for
the game's actual process DPI behavior**. Its core log still reported
`DISPLAY-DPI: DirectDraw physical=1920x1200 HWND monitor=1536x960 pixels
MISMATCH`. Menu surface mapping was correct; the HWND dimensions were not.

To restore **physical pixel geometry before HWND creation**, the unified
launcher now adds `HIGHDPIAWARE` to the **child process environment's**
`__COMPAT_LAYER` immediately before `CreateProcessW(CREATE_SUSPENDED)`,
then restores the parent's original environment as soon as the child is
created. It keeps unrelated compatibility layers, refuses a preexisting
`DPIUNAWARE` or `GDIDPISCALING` conflict, and never changes the registry,
global Windows DPI settings or the original retail executable.

A native Windows synthetic test confirmed actual DPI awareness:
- no manifest / no compatibility layer: process awareness **0** (unaware);
- no manifest / `HIGHDPIAWARE`: **2** (per-monitor aware);
- companion application manifest only: **1** (system aware).

Both 1 and 2 use physical coordinates for the game HWND. The runtime logs
`DISPLAY-DPI-CONTEXT: process=N hwnd=N window_dpi=N` and the expected
`DISPLAY-DPI ... MATCH`, as well as `BORDERLESS ... rect=...+1920x1200`.
The second monitor's potential DPI scale must still be tested; a real
Windows session is the acceptance gate, not a green synthetic CI run.

The companion manifest remains installer-owned for Windows/Wine fallbacks.
The new per-process compatibility layer removes the dependency on Windows
actually accepting the sidecar manifest on the supported Windows build.

## Unified Windows pointer and focus-pause fix

The mouse-disabled PCShell bit does not control the Windows OS pointer.
A real Windows test with two 1920×1200 monitors reported `cursor-showing=0`,
with `GetClipCursor=(0,-1200)-(1920,1200)` covering the full multi-monitor
desktop, not just the game window. The older cursor policy only showed the
pointer *after* focus loss, then explicitly called `ShowCursor(FALSE)` on
focus return. This made it unnecessarily difficult to leave the borderless
game by mouse, despite native game mouse polling already being disabled.

The **unified runtime only** restores the native arrow on its first
foreground Flip and whenever the mouse moves. The pointer stays available
on all monitors with **no capture**, but is automatically hidden after
**2.5 seconds without mouse motion while it rests inside the game HWND**.
Moving it again shows the cursor immediately and restarts the timeout.
Leaving the game's rectangle or switching to another window restores it
immediately, even if the focus-pause loop is blocking the game Flip.
No configuration setting, Windows timer, extra hook or polling thread is
required: it samples native cursor coordinates at the existing game Flip.

The hide uses a counted `ShowCursor(FALSE)` only for the game, balances
those calls with `ShowCursor(TRUE)` on mouse motion/exit/focus loss,
and never suppresses cursor visibility while another window owns focus.
If Windows reports a genuine game-only `ClipCursor` rectangle (equal
to the game HWND bounds but smaller than the virtual desktop), release
that game-specific confinement only while the game is foreground. The
full-desktop clip in the user log is NOT changed. Other windows and
the legacy runtime are not affected.

The focus-pause keyboard hook formerly called
`GetModuleHandleA("SpiderMan2k1Fix.dll")`, which stopped working when the
unified runtime was renamed `fix.dll`. Windows returned error 126 every
time an external window took focus; the game repeatedly attempted and
aborted the pause. The hook now obtains the owning module **from the real
keyboard callback address** (with `GetModuleHandleEx` and unchanged
reference count), and therefore works with legacy and unified DLL names.
The existing safety policy remains: pause only after confirmed focus loss,
let OS Alt+Tab pass, and resume only on a fresh key press+release after
the game regains focus (or the existing verified gamepad wake).

CI builds both runtimes and checks source/contract tests. Native Windows 11
logging and manual tests have confirmed cursor movement between monitors,
freeze of video and secondary audio on focus loss, and keyboard resume.
Wine/Proton confirmation of the unified architecture is still pending.
